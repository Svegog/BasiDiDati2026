Progetto Basi di Dati — Guida operativa (Django)

Dal Diagramma ER all'Applicativo Web Consegnabile

Percorso completo, passo per passo, per trasformare uno schema ER in un'applicazione web funzionante con Django e MySQL, pronta da comprimere in uno ZIP e consegnare.

1

Dal diagramma ER allo schema logico

Punto di partenza: il diagramma Entità-Relazione realizzato in DbMain. Prima di scrivere una sola riga di codice, va completata la progettazione logica, cioè la traduzione di entità e relazioni in tabelle relazionali (con chiavi primarie e chiavi esterne).

Tool utilizzato DbMain (o equivalente) per disegnare l'ER e generare automaticamente lo schema logico/relazionale a partire da esso.

Regole di traduzione principali da applicare (probabilmente già fatte nella relazione):

  • Ogni entità diventa una tabella.
  • Ogni attributo diventa una colonna.
  • Le associazioni 1-N diventano chiavi esterne nella tabella "N".
  • Le associazioni N-N diventano una tabella ponte con due chiavi esterne.
Se lo rifacessi da capo, cosa cambierei
  • Verificare che ogni tabella abbia una chiave primaria esplicita: Django, se non specificata, ne crea una automaticamente (id), ma se nello schema DbMain è già definita una chiave con un altro nome conviene dichiararla esplicitamente nel modello (Step 5) per restare fedeli alla relazione.
  • Annotare a parte i nomi definitivi di tabelle e colonne: in Django verranno mappati nei modelli Python, quindi conviene fissarli da subito per evitare di doverli rinominare in più punti.
2

Traduzione in DDL (CREATE TABLE)

Dallo schema logico si genera il codice SQL DDL (Data Definition Language): le istruzioni CREATE TABLE che creeranno fisicamente le tabelle nel database. Questo passaggio resta identico indipendentemente dal framework scelto in seguito.

Tool utilizzato DbMain può esportare direttamente il DDL nel dialetto SQL scelto (in questo caso MySQL). In alternativa si scrive manualmente seguendo lo schema logico.

Esempio di struttura attesa (adattare ai nomi reali delle proprie tabelle):

esempio 
CREATE TABLE Cliente (
    id_cliente INT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(50) NOT NULL,
    cognome VARCHAR(50) NOT NULL,
    telefono VARCHAR(20)
);

CREATE TABLE Ombrellone (
    id_ombrellone INT AUTO_INCREMENT PRIMARY KEY,
    numero INT NOT NULL,
    fila VARCHAR(10),
    stato VARCHAR(20)
);

CREATE TABLE Prenotazione (
    id_prenotazione INT AUTO_INCREMENT PRIMARY KEY,
    id_cliente INT NOT NULL,
    id_ombrellone INT NOT NULL,
    data_inizio DATE NOT NULL,
    data_fine DATE NOT NULL,
    FOREIGN KEY (id_cliente) REFERENCES Cliente(id_cliente),
    FOREIGN KEY (id_ombrellone) REFERENCES Ombrellone(id_ombrellone)
);
Cosa si può cambiare
  • Tipi di dato: usare DATE, DECIMAL(6,2) per importi, ENUM(...) per stati con valori fissi (es. stato ombrellone: libero/occupato/manutenzione) invece di VARCHAR generico.
  • Vincoli aggiuntivi: UNIQUE su un numero di ombrellone, NOT NULL su campi obbligatori, CHECK per vincoli di dominio (es. data_fine > data_inizio).
Nota specifica per Django Questo script .sql è comunque utile da conservare e consegnare nella relazione come documentazione dello schema, ma non sarà lo strumento con cui le tabelle verranno effettivamente create nel progetto: in Django questo compito lo svolgono i modelli e le migrations (Step 5 e 6).
3

Creazione del database in MySQL

Con Django non serve eseguire manualmente le CREATE TABLE: basterà creare il database vuoto, mentre le tabelle verranno generate automaticamente in seguito dalle migrations. Questo è uno dei vantaggi principali di Django rispetto a un framework minimale.

Tool utilizzato MySQL Workbench — usato qui solo per creare il database vuoto e, in seguito, per ispezionare visivamente le tabelle generate da Django.
  1. Apri Workbench e connettiti all'istanza locale (solitamente localhost, porta 3306).
  2. Crea una nuova query window (File > New Query Tab).
  3. Esegui solamente: CREATE DATABASE bagno_db CHARACTER SET utf8mb4;
  4. Non creare ancora le tabelle: ci penserà Django al Step 6.
Da tenere a mente
  • Il set di caratteri utf8mb4 è consigliato per evitare problemi con caratteri accentati o emoji nei testi inseriti dall'applicativo.
  • Lo script schema.sql dello Step 2 resta comunque utile da allegare alla relazione come documentazione, anche se Django userà un proprio meccanismo per creare le tabelle.
4

Creazione progetto Django

Con il database vuoto pronto, si crea il progetto Django e l'app che conterrà la logica del gestionale. In Django un "progetto" è il contenitore generale, mentre una "app" è un modulo funzionale al suo interno (qui ne basta una, es. bagno).

Tool/librerie utilizzate Python 3, Django (framework web), mysqlclient (libreria per collegare Django a MySQL).

Installazione (in un virtual environment, consigliato):

python -m venv venv
venv\Scripts\activate        # Windows
source venv/bin/activate     # Mac/Linux
pip install django mysqlclient

Creazione del progetto e dell'app:

django-admin startproject gestionale_bagno
cd gestionale_bagno
python manage.py startapp bagno

Struttura generata automaticamente:

gestionale_bagno/
├── manage.py
├── requirements.txt        (da creare a mano)
├── gestionale_bagno/        (cartella di configurazione progetto)
│   ├── settings.py
│   ├── urls.py
│   └── wsgi.py
└── bagno/                  (la nostra app)
    ├── models.py            (qui definiamo le tabelle)
    ├── views.py              (qui scriviamo la logica/query)
    ├── urls.py               (da creare, rotte dell'app)
    ├── admin.py              (pannello di amministrazione)
    └── migrations/           (storico delle modifiche al DB)

Registrare l'app in settings.py:

gestionale_bagno/settings.py 
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    'bagno',  # la nostra app
]

Configurare la connessione a MySQL (sempre in settings.py):

gestionale_bagno/settings.py 
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.mysql',
        'NAME': 'bagno_db',
        'USER': 'root',
        'PASSWORD': 'TUA_PASSWORD',
        'HOST': 'localhost',
        'PORT': '3306',
    }
}
Alternative possibili
  • Al posto di mysqlclient si può usare PyMySQL (più semplice da installare su alcuni sistemi, ma leggermente meno performante).
  • Se si preferisse un framework più minimale e con meno configurazione iniziale, l'alternativa naturale sarebbe Flask: Django conviene quando si vuole sfruttare l'admin panel automatico (Step 6) per gestire i dati senza scrivere form a mano.
5

Modelli Django e collegamento alle tabelle

In Django ogni tabella del database è rappresentata da una classe Python chiamata modello, definita in models.py. Django userà questa classe sia per generare la tabella SQL, sia per leggere/scrivere dati senza scrivere query manualmente (tramite l'ORM).

bagno/models.py 
from django.db import models

class Cliente(models.Model):
    id_cliente = models.AutoField(primary_key=True)
    nome = models.CharField(max_length=50)
    cognome = models.CharField(max_length=50)
    telefono = models.CharField(max_length=20, blank=True, null=True)

    class Meta:
        db_table = 'Cliente'  # forza il nome tabella esatto dello schema logico

    def __str__(self):
        return f"{self.nome} {self.cognome}"


class Ombrellone(models.Model):
    id_ombrellone = models.AutoField(primary_key=True)
    numero = models.IntegerField()
    fila = models.CharField(max_length=10, blank=True, null=True)
    stato = models.CharField(max_length=20, blank=True, null=True)

    class Meta:
        db_table = 'Ombrellone'

    def __str__(self):
        return f"Ombrellone {self.numero}"


class Prenotazione(models.Model):
    id_prenotazione = models.AutoField(primary_key=True)
    id_cliente = models.ForeignKey(Cliente, on_delete=models.CASCADE, db_column='id_cliente')
    id_ombrellone = models.ForeignKey(Ombrellone, on_delete=models.CASCADE, db_column='id_ombrellone')
    data_inizio = models.DateField()
    data_fine = models.DateField()

    class Meta:
        db_table = 'Prenotazione'
Punto critico da personalizzare
  • L'attributo db_table nella classe Meta è fondamentale: forza Django a usare esattamente il nome di tabella previsto dallo schema logico (Step 1), invece del nome generato di default (es. bagno_cliente). Coerenza con la relazione garantita.
  • Ogni associazione 1-N dello schema ER diventa un campo ForeignKey; le associazioni N-N diventano un ManyToManyField, oppure (consigliato per restare fedeli alla traduzione manuale) un modello a parte per la tabella ponte, come fatto sopra per Prenotazione.
  • Tipi di campo principali: CharField (testo breve), TextField (testo lungo), IntegerField, DecimalField (importi), DateField/DateTimeField, BooleanField.
6

Migrations e admin panel

Le migrations sono lo strumento con cui Django traduce i modelli Python in istruzioni CREATE TABLE reali, eseguite sul database MySQL. Sostituiscono il bisogno di scrivere manualmente il DDL in Workbench.

Tool utilizzato Comandi manage.py di Django (makemigrations, migrate) eseguiti da terminale; MySQL Workbench solo per verificare visivamente il risultato finale. 
python manage.py makemigrations
python manage.py migrate

Dopo questo comando, apri Workbench e verifica nel pannello Schemas che tutte le tabelle (Cliente, Ombrellone, Prenotazione, ecc.) siano state create automaticamente con le colonne previste.

Pannello di amministrazione automatico

Uno dei vantaggi principali di Django: registrando i modelli in admin.py, si ottiene gratuitamente un'interfaccia web per inserire/modificare/eliminare dati, senza scrivere form.

bagno/admin.py 
from django.contrib import admin
from .models import Cliente, Ombrellone, Prenotazione

admin.site.register(Cliente)
admin.site.register(Ombrellone)
admin.site.register(Prenotazione)

Creazione di un utente amministratore per accedervi:

python manage.py createsuperuser

Una volta avviato il server (Step 10), il pannello sarà raggiungibile su http://127.0.0.1:8000/admin.

Cosa si può cambiare
  • L'admin panel può bastare come "applicativo di gestione dati" se il tempo è poco, ma per un progetto completo conviene comunque costruire view e template personalizzati (Step 7-8) così da mostrare un'interfaccia pensata per l'utente finale, non solo per l'amministratore.
  • Si può personalizzare la visualizzazione nell'admin (es. colonne mostrate in lista) con la classe ModelAdmin, ma non è necessario per gli scopi dell'esame.
7

Traduzione delle query in view

In Django la logica delle pagine si scrive nelle view (file views.py). Ci sono due strade per "tradurre" le query già scritte in DbMain: usare l'ORM di Django (più idiomatico) oppure eseguire SQL puro (più fedele alle query originali). Di seguito entrambe, da scegliere secondo necessità della relazione.

Lettura (SELECT) — con ORM Django

from django.shortcuts import render
from .models import Cliente

def lista_clienti(request):
    clienti = Cliente.objects.all().order_by('cognome')
    return render(request, 'lista_clienti.html', {'clienti': clienti})

Lettura (SELECT) — con SQL puro (fedele a DbMain)

from django.db import connection

def lista_clienti(request):
    with connection.cursor() as cursor:
        cursor.execute("SELECT * FROM Cliente ORDER BY cognome")
        columns = [col[0] for col in cursor.description]
        clienti = [dict(zip(columns, row)) for row in cursor.fetchall()]
    return render(request, 'lista_clienti.html', {'clienti': clienti})

Inserimento (INSERT) — con ORM

from django.shortcuts import render, redirect

def nuovo_cliente(request):
    if request.method == 'POST':
        Cliente.objects.create(
            nome=request.POST['nome'],
            cognome=request.POST['cognome'],
            telefono=request.POST['telefono']
        )
        return redirect('lista_clienti')
    return render(request, 'form_cliente.html')

Modifica (UPDATE) ed eliminazione (DELETE) — con ORM

def modifica_cliente(request, id):
    cliente = Cliente.objects.get(id_cliente=id)
    if request.method == 'POST':
        cliente.nome = request.POST['nome']
        cliente.cognome = request.POST['cognome']
        cliente.save()
        return redirect('lista_clienti')
    return render(request, 'form_cliente.html', {'cliente': cliente})

def elimina_cliente(request, id):
    Cliente.objects.filter(id_cliente=id).delete()
    return redirect('lista_clienti')

Query con JOIN (relazioni tra tabelle)

Con l'ORM, una JOIN è spesso implicita seguendo le relazioni del modello:

def lista_prenotazioni(request):
    prenotazioni = Prenotazione.objects.select_related('id_cliente', 'id_ombrellone').all()
    return render(request, 'lista_prenotazioni.html', {'prenotazioni': prenotazioni})

Equivalente in SQL puro, più vicino a una query tradotta direttamente da DbMain:

cursor.execute("""
    SELECT c.nome AS nome_cliente, c.cognome AS cognome_cliente,
           o.numero AS numero_ombrellone, p.data_inizio, p.data_fine
    FROM Prenotazione p
    JOIN Cliente c ON p.id_cliente = c.id_cliente
    JOIN Ombrellone o ON p.id_ombrellone = o.id_ombrellone
""")

Collegare le view a un URL

bagno/urls.py (da creare) 
from django.urls import path
from . import views

urlpatterns = [
    path('', views.index, name='index'),
    path('clienti/', views.lista_clienti, name='lista_clienti'),
    path('clienti/nuovo/', views.nuovo_cliente, name='nuovo_cliente'),
    path('clienti/modifica/<int:id>/', views.modifica_cliente, name='modifica_cliente'),
    path('clienti/elimina/<int:id>/', views.elimina_cliente, name='elimina_cliente'),
    path('ombrelloni/', views.lista_ombrelloni, name='lista_ombrelloni'),
    path('prenotazioni/', views.lista_prenotazioni, name='lista_prenotazioni'),
]
gestionale_bagno/urls.py (da modificare) 
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('bagno.urls')),
]
Punto critico da personalizzare
  • Scegliere ORM se l'obiettivo è mostrare l'uso idiomatico di Django; scegliere SQL puro con connection.cursor() se l'obiettivo della relazione è dimostrare la fedeltà alle query tradotte da DbMain. È possibile anche mescolare i due approcci, usando SQL puro solo per le query più complesse (es. con aggregazioni o JOIN multiple).
  • Per ogni nuova entità dello schema (es. Stagione, Dipendente) si replica lo stesso blocco di view (lista, nuovo, modifica, elimina) e le relative righe in urls.py.

Template HTML e grafica

Django usa un proprio motore di template (sintassi molto simile a Jinja2): {{ variabile }} per i valori, {% %} per cicli e condizioni.

Tool/librerie utilizzate Sistema di template integrato in Django; Bootstrap 5 (via CDN) per la grafica di base senza scrivere CSS da zero.

Cartella dei template e configurazione necessaria:

bagno/
└── templates/
    ├── base.html
    ├── index.html
    ├── lista_clienti.html
    └── form_cliente.html

Verifica in settings.py che Django cerchi i template nelle app:

gestionale_bagno/settings.py 
TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [],
        'APP_DIRS': True,  # deve essere True
        ...
    },
]

Template base (eredita su tutte le pagine)

bagno/templates/base.html 
{% load static %}
<!DOCTYPE html>
<html lang="it">
<head>
    <title>{% block title %}Gestionale Bagno{% endblock %}</title>
    <link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css" rel="stylesheet">
    <link href="{% static 'style.css' %}" rel="stylesheet">
</head>
<body>
    <nav class="navbar navbar-dark bg-success">...</nav>
    <div class="container">
        {% block content %}{% endblock %}
    </div>
</body>
</html>

Pagina che estende il template base

bagno/templates/lista_clienti.html 
{% extends "base.html" %}
{% block content %}
<table class="table table-striped">
  <thead><tr><th>Nome</th><th>Cognome</th></tr></thead>
  <tbody>
  {% for c in clienti %}
    <tr><td>{{ c.nome }}</td><td>{{ c.cognome }}</td></tr>
  {% endfor %}
  </tbody>
</table>
{% endblock %}
Cosa si può cambiare
  • Nota la sintassi: con l'ORM si accede ai campi con il punto (c.nome), mentre con SQL puro restituito come dizionario si userà c.nome comunque se si convertono le righe in dizionari nella view (vedi Step 7), oppure c['nome'] se si passano dizionari direttamente: scegliere una convenzione e mantenerla coerente in tutto il progetto.
  • I file statici (CSS) vanno nella cartella static/ dentro l'app, e richiamati con {% static 'nomefile.css' %} dopo aver caricato {% load static %} in cima al template.
9

Personalizzare l'estetica

Come per qualsiasi framework web, la grafica si modifica senza toccare la logica applicativa, agendo solo su due punti: il foglio di stile CSS e il template base.

Cosa modificareDoveEsempio
Colori principali bagno/static/style.css .btn-primary { background-color: #0c4b33; }
Nome app, logo, voci di menu templates/base.html (sezione <nav>) Cambiare testo del brand e i link del menu
Tema colore navbar base.html, classe Bootstrap bg-success → bg-dark, bg-info...
Font style.css body { font-family: 'Segoe UI', sans-serif; }
Aspetto admin panel bagno/admin.py Personalizzare colonne con list_display in ModelAdmin
Suggerimento Bootstrap fornisce già classi pronte (card, table, btn, navbar...): modificarne i colori in CSS è molto più rapido che scrivere componenti da zero, ed è sufficiente per un progetto d'esame.
10

Test dell'applicativo

Con tutti i file pronti, si avvia il server di sviluppo Django:

python manage.py runserver

e si apre il browser su http://127.0.0.1:8000

Da verificare per ogni entità dello schema:

  • La lista si carica e mostra i dati corretti.
  • L'inserimento di un nuovo record funziona e appare nella lista.
  • La modifica aggiorna correttamente i dati esistenti.
  • L'eliminazione rimuove il record e non genera errori di vincolo (es. eliminare un cliente con prenotazioni attive, se non gestito, darà errore di chiave esterna: comportamento corretto da spiegare in relazione).
  • Il pannello /admin mostra correttamente tutti i modelli registrati.
Errore tipicoCausa
Access denied for userCredenziali errate in settings.py
Unknown databaseDatabase non creato in Workbench (Step 3)
No such tableMigrations non eseguite: lanciare makemigrations e migrate
NameError / NoReverseMatchNome route in urls.py non corrispondente a quello usato nel template
11

Preparazione dello ZIP finale

Ultimo passaggio prima della consegna:

  1. Fermare il server (Ctrl+C nel terminale).
  2. Eliminare la cartella venv/ (non va consegnata: pesante e non necessaria, le dipendenze si reinstallano con requirements.txt).
  3. Eliminare eventuali cartelle __pycache__/ (anche dentro bagno/migrations/, se presenti).
  4. Creare un file requirements.txt con: django e mysqlclient (con relative versioni, recuperabili con pip freeze).
  5. Selezionare tutti i file rimanenti della cartella progetto e comprimerli in un unico .zip.

Contenuto finale dello ZIP

gestionale_bagno/
├── manage.py
├── requirements.txt
├── schema.sql                  (documentazione, vedi Step 2)
├── gestionale_bagno/
│   ├── settings.py
│   ├── urls.py
│   └── wsgi.py
└── bagno/
    ├── models.py
    ├── views.py
    ├── urls.py
    ├── admin.py
    ├── migrations/
    ├── templates/
    │   └── *.html
    └── static/
        └── style.css

Da indicare nella relazione: per eseguire l'applicativo, creare il database vuoto in Workbench (CREATE DATABASE bagno_db), impostare le credenziali in settings.py, installare le dipendenze con pip install -r requirements.txt, eseguire le migrations con python manage.py migrate ed avviare il server con python manage.py runserver.
