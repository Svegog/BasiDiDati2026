Progetto Basi di Dati — Guida operativa

Dal Diagramma ER all'Applicativo Web Consegnabile

Percorso completo, passo per passo, per trasformare uno schema ER in un'applicazione web funzionante con Flask e MySQL, pronta da comprimere in uno ZIP e consegnare.

1

Dal diagramma ER allo schema logico

Punto di partenza: il diagramma Entità-Relazione realizzato in DbMain. Prima di scrivere una sola riga di codice, va completata la progettazione logica, cioè la traduzione di entità e relazioni in tabelle relazionali (con chiavi primarie e chiavi esterne).

Tool utilizzato DbMain (o equivalente) per disegnare l'ER e generare automaticamente lo schema logico/relazionale a partire da esso.

Regole di traduzione principali da applicare (probabilmente già fatte nella relazione):

  • Ogni entità diventa una tabella.
  • Ogni attributo diventa una colonna.
  • Le associazioni 1-N diventano chiavi esterne nella tabella "N".
  • Le associazioni N-N diventano una tabella ponte con due chiavi esterne.
Se lo rifacessi da capo, cosa cambierei
  • Verificare che ogni tabella abbia una chiave primaria esplicita (anche se DbMain lo fa di default), preferibilmente un intero auto-incrementale, per semplificare poi le query in Flask.
  • Annotare a parte i nomi definitivi di tabelle e colonne: verranno riutilizzati identici in tutto il codice Python e HTML, quindi conviene fissarli da subito per evitare di doverli cambiare in più punti.
2

Traduzione in DDL (CREATE TABLE)

Dallo schema logico si genera il codice SQL DDL (Data Definition Language): le istruzioni CREATE TABLE che creeranno fisicamente le tabelle nel database.

Tool utilizzato DbMain può esportare direttamente il DDL nel dialetto SQL scelto (in questo caso MySQL). In alternativa si scrive manualmente seguendo lo schema logico.

Esempio di struttura attesa (adattare ai nomi reali delle proprie tabelle):

esempio 
CREATE TABLE Cliente (
    id_cliente INT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(50) NOT NULL,
    cognome VARCHAR(50) NOT NULL,
    telefono VARCHAR(20)
);

CREATE TABLE Ombrellone (
    id_ombrellone INT AUTO_INCREMENT PRIMARY KEY,
    numero INT NOT NULL,
    fila VARCHAR(10),
    stato VARCHAR(20)
);

CREATE TABLE Prenotazione (
    id_prenotazione INT AUTO_INCREMENT PRIMARY KEY,
    id_cliente INT NOT NULL,
    id_ombrellone INT NOT NULL,
    data_inizio DATE NOT NULL,
    data_fine DATE NOT NULL,
    FOREIGN KEY (id_cliente) REFERENCES Cliente(id_cliente),
    FOREIGN KEY (id_ombrellone) REFERENCES Ombrellone(id_ombrellone)
);
Cosa si può cambiare
  • Tipi di dato: usare DATE, DECIMAL(6,2) per importi, ENUM(...) per stati con valori fissi (es. stato ombrellone: libero/occupato/manutenzione) invece di VARCHAR generico.
  • Vincoli aggiuntivi: UNIQUE su un numero di ombrellone, NOT NULL su campi obbligatori, CHECK per vincoli di dominio (es. data_fine > data_inizio).
3

Creazione del database in MySQL

Il DDL prodotto al passo precedente viene eseguito concretamente su MySQL Community Server, usando MySQL Workbench come interfaccia grafica.

Tool utilizzato MySQL Workbench — editor SQL grafico per connettersi al server, eseguire script ed esplorare le tabelle create.
  1. Apri Workbench e connettiti all'istanza locale (solitamente localhost, porta 3306).
  2. Crea una nuova query window (File > New Query Tab).
  3. Esegui prima CREATE DATABASE bagno_db; e poi USE bagno_db;
  4. Incolla ed esegui tutte le CREATE TABLE (Step 2), rispettando l'ordine: prima le tabelle senza chiavi esterne, poi quelle che le referenziano.
  5. Verifica nel pannello Schemas a sinistra che tutte le tabelle siano comparse correttamente.
Da tenere a mente
  • Se si modifica lo schema in seguito (es. si aggiunge una colonna), va rieseguita la modifica anche su Workbench: lo script .sql e il database reale devono restare sincronizzati.
  • È utile salvare lo script SQL finale in un file (es. schema.sql) da includere nella consegna, così chi riceve il progetto può ricreare il database identico.
4

Struttura del progetto Flask

Con il database pronto, si passa alla parte applicativa. Flask è un micro-framework Python per applicazioni web: richiede poca configurazione e si integra bene con query SQL scritte a mano (utile per mostrare la coerenza con il lavoro di traduzione già svolto in DbMain).

Tool/librerie utilizzate Python 3, Flask (framework web), mysql-connector-python (libreria per collegare Python a MySQL).

Struttura di cartelle e file da creare:

gestionale_bagno/
├── app.py              (route e logica dell'applicazione)
├── db.py               (funzioni di connessione al database)
├── config.py           (credenziali di accesso a MySQL)
├── schema.sql           (script DDL dello Step 2-3)
├── requirements.txt     (elenco librerie da installare)
├── templates/            (pagine HTML)
│   ├── base.html
│   ├── index.html
│   └── ...
└── static/
    └── style.css         (grafica)

Contenuto di requirements.txt:

requirements.txt 
Flask==3.0.3
mysql-connector-python==9.0.0

Installazione (in un virtual environment, consigliato):

python -m venv venv
venv\Scripts\activate        # Windows
source venv/bin/activate     # Mac/Linux
pip install -r requirements.txt
Alternative possibili
  • Al posto di mysql-connector-python si potrebbe usare PyMySQL oppure SQLAlchemy come ORM: quest'ultimo nasconde le query SQL dietro oggetti Python, comodo ma meno trasparente se l'obiettivo è mostrare la traduzione diretta dalle query DbMain.
  • Al posto di Flask si potrebbe usare Django (più strutturato ma più lento da configurare per un progetto di questa dimensione).

Connessione Python ↔ MySQL

Si centralizzano credenziali e funzioni di accesso al database in due file separati, in modo da non ripetere codice in ogni route.

config.py 
DB_CONFIG = {
    'host': 'localhost',
    'port': 3306,
    'user': 'root',
    'password': 'TUA_PASSWORD',
    'database': 'bagno_db'
}
db.py 
import mysql.connector
from flask import g
from config import DB_CONFIG

def get_db():
    db = getattr(g, '_database', None)
    if db is None:
        db = g._database = mysql.connector.connect(**DB_CONFIG)
    return db

def query_db(query, args=(), one=False, commit=False):
    db = get_db()
    cur = db.cursor(dictionary=True)  # righe leggibili come dizionari
    cur.execute(query, args)
    if commit:
        db.commit()
        cur.close()
        return None
    rv = cur.fetchall()
    cur.close()
    return (rv[0] if rv else None) if one else rv

def close_db(exception=None):
    db = getattr(g, '_database', None)
    if db is not None:
        db.close()
Perché questa struttura
  • dictionary=True permette di leggere le colonne per nome nei template (es. riga['nome']) invece che per indice numerico: più leggibile e meno soggetto a errori se si modifica l'ordine delle colonne.
  • La connessione è salvata in g (oggetto di contesto di Flask) e chiusa automaticamente a fine richiesta, evitando connessioni aperte inutilmente.
6

Traduzione delle query in route

Ogni operazione CRUD (Create, Read, Update, Delete) sulle tabelle dello schema logico diventa una route Flask, cioè un URL associato a una funzione Python che esegue la query e restituisce una pagina HTML.

Lettura (SELECT)

@app.route('/clienti')
def lista_clienti():
    clienti = query_db("SELECT * FROM Cliente ORDER BY cognome")
    return render_template('lista_clienti.html', clienti=clienti)

Inserimento (INSERT)

@app.route('/clienti/nuovo', methods=['GET', 'POST'])
def nuovo_cliente():
    if request.method == 'POST':
        query_db(
            "INSERT INTO Cliente (nome, cognome, telefono) VALUES (%s, %s, %s)",
            (request.form['nome'], request.form['cognome'], request.form['telefono']),
            commit=True
        )
        return redirect(url_for('lista_clienti'))
    return render_template('form_cliente.html', cliente=None)

Modifica (UPDATE) ed eliminazione (DELETE)

Stesso schema: query parametrizzata con %s, eseguita con commit=True.

query_db("UPDATE Cliente SET nome=%s, cognome=%s WHERE id_cliente=%s",
         (nome, cognome, id), commit=True)

query_db("DELETE FROM Cliente WHERE id_cliente=%s", (id,), commit=True)

Query con JOIN (relazioni tra tabelle)

prenotazioni = query_db("""
    SELECT c.nome AS nome_cliente, c.cognome AS cognome_cliente,
           o.numero AS numero_ombrellone, p.data_inizio, p.data_fine
    FROM Prenotazione p
    JOIN Cliente c ON p.id_cliente = c.id_cliente
    JOIN Ombrellone o ON p.id_ombrellone = o.id_ombrellone
""")
Punto critico da personalizzare
  • I nomi di tabelle e colonne nelle query devono corrispondere esattamente a quelli creati nello Step 3. Conviene copiare le query già tradotte da DbMain piuttosto che riscriverle a mano, per evitare incongruenze.
  • Usare sempre %s come segnaposto (mai concatenare stringhe con i valori dell'utente): previene errori di sintassi e vulnerabilità di SQL injection.
  • Per ogni nuova entità dello schema (es. Stagione, Dipendente) si replica lo stesso blocco di 4 route: lista, nuovo, modifica, elimina.

Template HTML e grafica

Flask usa il motore di template Jinja2: permette di inserire dati Python dentro file HTML con la sintassi {{ variabile }} e cicli/condizioni con {% %}.

Tool/librerie utilizzate Jinja2 (incluso in Flask) per i template; Bootstrap 5 (via CDN) per la grafica di base senza scrivere CSS da zero.

Template base (eredita su tutte le pagine)

templates/base.html 
<!DOCTYPE html>
<html lang="it">
<head>
    <title>{% block title %}Gestionale Bagno{% endblock %}</title>
    <link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css" rel="stylesheet">
    <link href="{{ url_for('static', filename='style.css') }}" rel="stylesheet">
</head>
<body>
    <nav class="navbar navbar-dark bg-primary">...</nav>
    <div class="container">
        {% block content %}{% endblock %}
    </div>
</body>
</html>

Pagina che estende il template base

templates/lista_clienti.html 
{% extends "base.html" %}
{% block content %}
<table class="table table-striped">
  <thead><tr><th>Nome</th><th>Cognome</th></tr></thead>
  <tbody>
  {% for c in clienti %}
    <tr><td>{{ c['nome'] }}</td><td>{{ c['cognome'] }}</td></tr>
  {% endfor %}
  </tbody>
</table>
{% endblock %}
Cosa si può cambiare
  • I nomi delle colonne nelle celle (c['nome']) devono coincidere con gli alias usati nella query SELECT.
  • Si possono aggiungere colonne calcolate direttamente nella query (es. durata soggiorno) e visualizzarle senza modificare la logica Python.
8

Personalizzare l'estetica

La grafica si modifica senza toccare la logica applicativa, agendo solo su due punti: il foglio di stile CSS e il template base.

Cosa modificareDoveEsempio
Colori principali static/style.css .btn-primary { background-color: #0e7490; }
Nome app, logo, voci di menu templates/base.html (sezione <nav>) Cambiare testo del brand e i link del menu
Tema colore navbar base.html, classe Bootstrap bg-primary → bg-dark, bg-info...
Font style.css body { font-family: 'Segoe UI', sans-serif; }
Layout homepage templates/index.html Aggiungere/rimuovere le card di riepilogo
Suggerimento Bootstrap fornisce già classi pronte (card, table, btn, navbar...): modificarne i colori in CSS è molto più rapido che scrivere componenti da zero, ed è sufficiente per un progetto d'esame.

Test dell'applicativo

Con tutti i file pronti, si avvia il server di sviluppo Flask:

python app.py

e si apre il browser su http://127.0.0.1:5000

Da verificare per ogni entità dello schema:

  • La lista si carica e mostra i dati corretti.
  • L'inserimento di un nuovo record funziona e appare nella lista.
  • La modifica aggiorna correttamente i dati esistenti.
  • L'eliminazione rimuove il record e non genera errori di vincolo (es. eliminare un cliente con prenotazioni attive, se non gestito, darà errore di chiave esterna: comportamento corretto da spiegare in relazione).
Errore tipicoCausa
Access denied for userCredenziali errate in config.py
Unknown databaseSchema non ancora creato in Workbench
1146: Table doesn't existNome tabella errato o maiuscole/minuscole diverse
Pagina bianca / errore 500Errore di sintassi SQL: testare la query isolata in Workbench

Preparazione dello ZIP finale

Ultimo passaggio prima della consegna:

  1. Fermare il server (Ctrl+C nel terminale).
  2. Eliminare la cartella venv/ (non va consegnata: pesante e non necessaria, le dipendenze si reinstallano con requirements.txt).
  3. Eliminare eventuali cartelle __pycache__/.
  4. Selezionare tutti i file rimanenti della cartella progetto e comprimerli in un unico .zip.

Contenuto finale dello ZIP

gestionale_bagno/
├── app.py
├── config.py
├── db.py
├── schema.sql
├── requirements.txt
├── templates/
│   └── *.html
└── static/
    └── style.css

Da indicare nella relazione: per eseguire l'applicativo, creare il database con schema.sql in Workbench, impostare le credenziali in config.py, installare le dipendenze con pip install -r requirements.txt ed eseguire python app.py.
