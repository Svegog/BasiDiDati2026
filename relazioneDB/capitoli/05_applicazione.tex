\section{Funzionalit\`{a} implementate}

\subsection{Autenticazione}
Il proprietario accede al sistema tramite email e password, verificate con una
query SQL diretta sulla tabella \texttt{PROPRIETARIO}. La password \`{e}
confrontata in chiaro, scelta effettuata per un database locale e semplicità di implementazione.

Non viene utilizzato il sistema utenti integrato di Django \textbf{django.contrib.auth.User}, ma 
la lettura della tabella \entita{PROPRIETARIO} nel database con query SQL diretta.

La sessione viene mantenuta tramite il framework di sessioni di
Django (cookie), configurato per scadere alla chiusura del browser. Ogni form
\`{e} protetto da CSRF tramite il token integrato di Django.

\subsection{Interfaccia e navigazione}

Ogni pagina non principale (come le sezioni adibite alle query) estende \textbf{base.html} e 
aggiunge un \textit{block content}.

I partial delle singole azioni (form, risultati query) vengono caricati 
dentro un'area specifica via HTMX, senza ricaricare tutta la pagina.

La dashboard espone le tre aree applicative (Spiaggia, Ordini, Turni) tramite
pulsanti che caricano la relativa pagina via HTMX.

All'interno di ciascuna area, un menu laterale distingue le operazioni di inserimento/modifica
\textit{Servizi} dalle query di controllo \textit{Controlli}: le prime vengono
mostrate in un pannello centrale, le seconde in un pannello laterale che
appare solo quando contiene un risultato. Un clic sullo stesso pulsante
richiude il pannello corrispondente, riportando l'interfaccia allo stato
iniziale.

\subsection{Operazioni implementate}
Sono state implementate le stesse operazioni descritte nella sezione~\ref{sec:operazioniPrincipali}, 
con qualche aggiunta effettuata per comodità come:
\begin{itemize}
  \item Check del \entita{Catalogo} di dato un \entita{Fornitore}
  \item Modifica di inserimento \entita{Ordine} e nuovo fornitore per aggiungere più \entita{Prodotti} alla volta 
  (l'aggiunta di un solo elemento a richiesta risultava ripetitivo)
\end{itemize}

\subsection{Descrizione Front-End}

Come mostrato nella figura sottostante, si è deciso di dividere l'applicativo in tre aree:
\begin{itemize}
  \item \textbf{Area operazioni} (laterale sinistra)\textbf{:} contiene una breve descrizione 
  dell'operazione da effettuare e il pulsante associato, che sono state divise in:
  \begin{enumerate}
    \item \textbf{Servizi:} query di inserimento
    \item \textbf{Controlli:} query di ricerca
  \end{enumerate}
  \item \textbf{Area form} (centrale)\textbf{:} contiene il form mostrato all'utente dove 
  inserire i valori necessari alle query
  \item \textbf{Area risultati} (laterale destro)\textbf{:} mostra il risultato di query di 
  consultazione, principalmente sotto forma di tabelle formattate con CSS. Se nessuna opzione
  di consultazione viene selezionata, quest'area collassa lasciando spazio ai form.
\end{itemize}

Form di inserimento e consultazione possono essere aperti in contemporanea: questa scelta
è stata inserita per risolvere problemi come: \textit{Quali ombrelloni posso prenotare?} \\
Basta visualizzare nell'area risultati gli ombrelloni disponibili, inserendo nel form 
di prenotazione \textit{CodFila} e \textit{NumOmbrellone} ottenuti. \\ \\
I vari errori, warning o successi sono gestiti con pop-up in basso a destra ( tramite \textit{Toast JS} ) 
per notificare l'utente se un'operazione è andata a buon fine oppure no.
